## Friction Points

1. **Reviewer disagreement with no adjudication protocol.** Black Panther and Loki both reported findings on the same files and contradicted each other on 2 of 7 points. No built-in mechanism to surface the disagreement or force a tie-breaker. Main agent had to manually cross-check via filesystem reads. → Suggestion: add a "consensus" step to `/aegis-team-review` where a third agent (or the main agent) explicitly reconciles conflicting findings before anything is committed. Or: require reviewers to cite evidence (file:line, bash output) so disagreements surface with facts, not just assertions.

2. **Subagent tool availability not discoverable from spec.** The `memory-tool-integration.md` spec assumed `memory_20250818` would be usable from the Nick Fury subagent. It isn't — only the main agent gets it. This is the third consecutive session where "only dogfooding reveals it" (per P-006). → Suggestion: add a "tool availability assumptions" section to every v9 spec, and run a pre-flight check (grep agent definitions for `tools:` list) before committing to a design.

3. **Self-enforcement blocks its own framework updates, recurring.** Guard-write.sh has blocked: (a) settings.json edit last session, (b) `.claude/hooks/` write last session, (c) `.claude/agents/spider-man.md` edit this session. Each time, the agent pivoted to staging in `tools/` with a between-session manual step. That's now 3 manual steps accumulated: `apply-session-hook-settings.sh`, `v9-05-spider-man-worktree-guidance.md` (needs manual apply), and last session's settings hardening (now done). → Suggestion: introduce a principled `AEGIS_MAINTAINER_MODE=1` environment flag that temporarily widens guard-write for explicit framework-file paths during a single tool call. Require explicit user invocation (not agent-self-grant). Document the threat model (agent could weaponize the flag if compromised) and mitigations (single-tool-call scope, audit log, cannot be set by subagents).

4. **MEMORY.md scope conflict silently coexists with Claude Code's user-scoped memory system.** Until I added the header note, nothing in the repo documented the relationship between `.aegis/brain/MEMORY.md` (repo-scoped) and `~/.claude/projects/.../memory/` (user-scoped). A future agent reading only the scope-less file would guess wrong. The note I added is a 1-line patch, but the underlying issue (two independent memory systems coexisting without a contract) is deeper. → Suggestion: ADR this. Document which system owns what data classes (team conventions vs personal preferences), and write an AEGIS instinct about never auto-writing to user-scoped memory from repo-scoped tools.

5. **The "7 commits ahead of origin" state.** Tree is clean, all commits signed, reviewer checks passed — yet I'm explicitly NOT pushing because Golden Rule #2 says branch + PR. There's no branch. For a solo-maintainer meta-repo where the "PR" step is just self-review, the rule creates friction without the safety benefit. → Suggestion: add a resonance memory clarifying when #2 applies (shared repos with multiple maintainers) vs when it doesn't (solo maintainer with audit trail in retros), OR soften the rule to "never force-push to main; always require explicit user approval to push to main". Current phrasing forces a ceremony that adds no safety in this context.
